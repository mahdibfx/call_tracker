Push notifications, and the real package name4 Novneeds device

lib/data/push_service.dart · main.dart · auth_service.dart · root_view.dart · firebase_options.dart · android/app/ (build.gradle.kts, google-services.json, AndroidManifest.xml, MainActivity.kt)

Push is in. A new report in your role's categories, or a decision on one you filed, now reaches the phone while the app is backgrounded or closed. Tapping the notification opens that report. Android only — there is no iOS Firebase app.

It runs on the elameed-system Firebase project, the same one the Teachers App uses, as its own Android app com.elameed.staff. The backend sends a title and body, so Android draws the tray entry itself; no local-notifications plugin was needed. While the app is open the tray entry is suppressed, so an arriving push refreshes the list instead of drawing a banner over what you are reading.

The device is registered when a session begins — a fresh sign-in and a restored one both go through the same hook — and unregistered on sign-out, so a shared handset stops showing the previous user's reports.

The package name changed from com.example.call_tracker to com.elameed.staff. Play rejects com.example.*, so this had to happen before any release. It means this build installs beside an older one rather than over it: remove the old app first, and expect to sign in again.

How to test
  1. Install on a real phone. Android 13+ should ask for notification permission on the first sign-in.
  2. From another account (or the dashboard), file a report in a category this user's role handles. With the app backgrounded, a notification should arrive.
  3. Tap it: the app should open that report, not just the list.
  4. Force-close the app entirely, repeat, and tap again — the cold-start path is separate code and is the one most likely to break.
  5. With the app open on the list, have a report filed: no banner, but the list should refresh on its own.
  6. Sign out, then have another report filed: nothing should arrive on this phone.
A debug APK builds with the renamed package and the new Firebase config. flutter analyze clean, 117 tests pass.
Nothing about push can be verified without a handset and a second account — no notification has actually been delivered yet. The backend also has to be told this new Firebase app exists if it holds per-app credentials.
App icon, camera-only photos, and a report error that says what went wrong29 Octneeds device

assets/icon/ · pubspec.yaml · lib/data/photo_capture.dart · report_api.dart · lib/ui/views/reports/report_compose_view.dart

App icon. The app had the stock Flutter icon. It now has a staff ID badge on the brand orange, generated into every Android density, the adaptive icon (orange background, badge foreground) and the iOS set. The source is assets/icon/app_icon.svg; after editing it, re-render the PNGs and run dart run flutter_launcher_icons.

Camera only. The gallery card is gone from the compose screen and PhotoCapture.choosePhoto is deleted. A report has to be photographed where the problem is, not attached from a screenshot days later. This is a deliberate divergence from the dashboard's modal, which still offers both.

The real error. Sending a report that the server refused showed “Check your connection and try again” no matter what actually happened — createReport collapsed every failure into null. It now returns the reason and the screen shows the server's own message, so a rejection reads as a rejection and only a genuinely unreachable server blames the connection. A 2xx whose body cannot be parsed now counts as sent, so nobody files the same report twice.

How to test
  1. Install over the old build: the home screen icon should be the orange badge, not the Flutter logo. Check the app switcher and the settings list too.
  2. Compose a report: there is one photo card and it opens the camera. There is no way to reach the gallery.
  3. Send a report with a photo — this is what was failing. It should go through now.
  4. Close a report with a result photo: the same upload bug applied there, so that path needs a run too.
  5. Turn airplane mode on and send: it should say it could not reach the server, which is the one case where that wording is true.

The cause, found. Not the network. MultipartFile.fromPath labels a file application/octet-stream unless told otherwise, and the backend's upload filter answers 400 “The file must be an image.” — so every report carrying a photo was refused while text-only ones went through. Both upload paths now name the type. Confirmed against production by curl: the same request succeeds as image/jpeg and fails as application/octet-stream.

Reports with a photo, without a photo, and with a room were all accepted (201) by the live API as anis@gmail.com. test/report_upload_test.dart pins the content type so this cannot come back.
Reports: file one, and handle your role's27 Octneeds device

lib/data/report_models.dart · report_api.dart · photo_capture.dart · lib/ui/views/reports/ (inbox, detail, compose + 6 widgets)

What changed. The Reports tab is real. Everyone can file a report with a description, a photo, a category and optionally a room. Whoever's role owns that category can then work it: Start work, then Close with a result note and a result photo, or reopen a closed one. Admins can additionally sign a report off, and see every category.

Visibility is left to the backend — own-role categories plus anything you filed yourself, or everything for an admin — so the app never filters the list itself. Only the action buttons are gated on the device, and that gate is cosmetic: a 403 is surfaced as a readable message rather than swallowed.

The compose screen mirrors the dashboard's report modal, so the two read as the same thing: a flag header, a dashed photo card, every category as a chip, the description, and an optional room. Captures are downscaled (quality 70, max width 1920) because phone cameras produce 5–12 MB frames and the backend refuses anything over 10 MB — there is also a client-side size check, so an oversized file fails instantly instead of after a two-minute upload.

All 23 categories are shown, alphabetically, and one is required — it is what routes the report. Deliberately not filtered to the reporter's own role, since that would stop a cleaner reporting a broken projector. The send button stays disabled until there is a category plus a photo or a description, and the hint beneath it names whichever is still missing.

How to test
  1. As a cleaner or maintenance account: the app opens straight onto Reports with no bottom bar.
  2. Tap +, pick a category, type a description, take a photo, pick a room, send. The report should appear at the top of the list.
  3. Try to send with neither a description nor a photo — the button stays disabled and says why.
  4. Open a report in your role's category: Start work → Close this report → choose Done, add a note and a result photo. The result block should then show both.
  5. Open a report in another role's category (e.g. a cleaner opening a plumbing one): it must be readable with no action buttons at all.
  6. Reopen a completed report and confirm it goes back to In progress.
  7. As an admin: sign a report off, then take the sign-off back. A tick should appear beside the state while signed off.
  8. Filter by each state chip; pull down to refresh; scroll past 50 reports to check the next page loads.
  9. Turn airplane mode on and pull to refresh: the list must keep what it had and say it could not load, not go blank.
Covered by tests
  • test/report_parsing_test.dart — 24 checks against live payload shapes: every nullable field absent, unknown states, unusable rows dropped, who may handle what (including the two role spellings agreeing), and the flat /reports pagination that Paged.fromJson would have read as a single page.
  • test/report_actions_test.dart — 13 widget checks pinning the permission matrix in the UI: which buttons each role sees, how the offered transitions follow the state, and sign-off being admin-only.
Every field the app reads was confirmed present in production responses for /reports, /report-categories, /rooms and /reports/categories.
Nothing here has been seen on a screen, and the camera path in particular cannot be exercised without a handset. Push notifications are still to come, so a new report only appears on someone else's phone when they open or refresh the app.
Choose which number to ring27 Octneeds device

lib/ui/views/student_detail/widgets/number_picker_sheet.dart · student_detail_view.dart · call_view.dart · call_monitor.dart · models.dart · students_view.dart · groups_view.dart

What changed. Students can have more than one number on file (a personal line and a parent line). The app used to pick one silently. Now: one number dials straight away as before, and two or more opens a sheet listing each line with its personal/parent label. The line the app would have picked — the parent, who is who agents are usually ringing — is highlighted with a tick. One tap places the call; there is no confirm button.

List rows now read 0782720884  +1 when a student has other lines, so the choice is not a surprise. The finished-call summary shows the number actually rung rather than re-running the precedence rules.

Why this one needs real-device attention. CallMonitor.reconcile finds the call in the device's call log by the dialed string. The chosen number is now passed down explicitly — picker → CallView → PendingCall → dialer → lookup — and is never re-derived. If it ever diverged, a parent-line call would be looked up under the personal number, come back missing, and flag the agent for a call they really made. Unit tests pin the thread, but only a real call proves it.
How to test
  1. Open a student with two numbers — e.g. 102 مريم البتول, 196 شهد, or 197 أيوب on the live roster.
  2. Confirm the list row showed +1 before you opened them.
  3. Tap Start Call: the sheet lists both lines, the parent one ticked.
  4. Pick the parent line and let the call connect, then end it. The summary must show the parent number, and the call must not come back flagged as never placed.
  5. Repeat picking the personal line — same check.
  6. Dismiss the sheet by tapping outside: no call should be placed.
  7. Open a student with one number: it must dial immediately, with no sheet.
  8. Force-close the app mid-call on a parent-line call, then reopen it: the recovered summary must still show the parent number.
Covered by tests
  • test/number_picker_test.dart — 12 checks: the one-line vs multi-line branch, the parent being the suggested line, phoneSummary, PendingCall round-tripping both the number and which line it was, a pre-picker record defaulting to personal, the summary narrowing, and three widget tests on the sheet (renders both lines labelled, one tap returns the non-suggested line, dismissal returns null).
Staff app: one login, routed by role27 Octneeds device

lib/data/models.dart · api_service.dart · auth_service.dart · main.dart · lib/ui/views/root/app_area.dart · root_view.dart · bottom_nav_bar.dart · app_top_bar.dart

What changed. The app is now the staff app. Login moved to the unified POST /Auth/login, which returns the account's role and whether it is a call-tracker agent, and issues one token that works on every route the app uses. What the user sees is decided from that:

RoleWith an agent idWithout
admin · team onsite · team onlineCalls, Groups, History, ReportsReports only
cleaner · maintenance—Reports only
teacherrefused, pointed at the Teachers app

Calls keys on agent_id, not seniority: POST /call-tracker/calls refuses accounts without one, so an admin who was never provisioned as an agent gets no dialer rather than a dialer that fails on submit. Roles with a single area get that screen with no bottom bar. The top bar now shows who is signed in — initials and role — in the slot that used to hold a hamburger that did nothing. The Dashboard tab is gone from the shell (the file is kept; it was an undesigned placeholder).

Test this before anything else ships. On a device that already has the old build installed, upgrade in place and open the app. The stored session predates roles, so it is completed against POST /Token/verifyToken using the existing token — the user should land in the app without signing in again, after a brief spinner. If they get bounced to the login screen, the migration did not work and every agent in the field will be signed out by this release.
How to test
  1. Upgrade path (above) — the highest-risk item in this release.
  2. Sign in as an agent-enabled office account: four tabs, calls behave exactly as before.
  3. Sign in as a cleaner or maintenance account: Reports only, no bottom bar, and the top-right avatar still logs out — it is their only chrome.
  4. Sign in as a teacher: refused, with the message naming the Teachers app, and no session left behind (reopening the app must not let them in).
  5. Check the launcher icon label now reads El Ameed Staff, and the login screen says Staff Login rather than naming the call tracker.
Covered by tests
  • test/staff_role_test.dart — the role normaliser (team onsite and team_onsite resolving alike), the login payload parser, and session round-tripping.
  • test/app_area_test.dart — which areas each role gets, including an admin without an agent id getting no dialer, and a loop so a seventh role added later inherits the rule.
  • test/auth_flow_test.dart — a pre-role session restores without throwing; corrupt sessions are discarded rather than crashing startup (this path previously could leave the app with no first frame at all).
Verified against production with curl: the unified token returns 200 on /call-tracker/students, /call-tracker/groups, /ManagementStudent/student-calls/:id, /groups/:id/students, /reports, /report-categories, /rooms and /devices. This retires the 403 that blocked the per-student call log below — that entry is now unblocked.
Not yet done, tracked rather than forgotten: the Reports screens (the tab is a placeholder), camera capture for report photos, and push notifications.
Per-student call log14 Octneeds device

lib/data/models.dart · lib/data/api_service.dart · lib/ui/views/student_calls/student_calls_view.dart · lib/ui/views/student_detail/student_detail_view.dart

What changed. The client wanted a call log per student rather than the global one. The history icon on the student detail card was decorative — it now opens a Call Log screen listing every call ever made to that student, by anyone, newest first, from GET /ManagementStudent/student-calls/:id. Pull to refresh.

Each row shows date and time, talk duration (or "Not answered"), reason, who placed the call (called_by.name), the outcome as a pill, and the agent's notes.

Per the project rule, nothing verdict-derived is rendered: verdict, final_result, likely_hung_up_early and ended_quickly come back in the payload and are deliberately not parsed. The existing History tab (the agent's own calls, read from the device) is unchanged.

Unblocked as of 27 Oct. The 403 came from the retired POST /call-tracker/auth/login token. The app now signs in through the unified POST /Auth/login, whose token returns 200 on both GET /ManagementStudent/student-calls/:id and GET /groups/:id/students — confirmed with curl against production. Both this screen and the group roster should now load.
How to test
  1. Sign in as an agent, open Students, tap any student.
  2. Tap the history icon at the top right of the student card.
  3. A student who has been called shows the list newest first; check the duration reads "Not answered" for a 0-second call.
  4. Pull down to refresh.
  5. Open a student nobody has called — expect "No calls to this student yet.", still pull-to-refreshable.
  6. Confirm no row mentions a verdict, a flag, or anything about a call-log check.
Already covered by tests
  • test/student_call_test.dart — 5 checks against the documented row: epoch arriving as a string, the "0" epoch falling back to created_at for pre-September calls, unusable rows dropped instead of dated 1970, missing called_by, and talk time (not the verdict fields) deciding answered.
  • flutter analyze clean · flutter test 30/30.
Verified against the live endpoint with an office token, so the parsing matches real data (including Arabic names). Nobody has seen the screen on a handset.
