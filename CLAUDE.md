# call_tracker

- Flutter is not on `PATH`. Use the fvm copy: `export PATH="/Users/mahdi/fvm/versions/3.38.1/bin:$PATH"` before `flutter analyze` / `flutter test` / `flutter build apk --debug`.
- No emulator is configured — the only mobile device is a wirelessly-connected physical iPhone, and the app is Android-first (`phone_state`, native dialer intent), so UI behaviour cannot be verified locally. Analyze + tests + a debug APK build is as far as automated verification goes.
- The four tabs live in an `IndexedStack` in `root_view.dart`, so a tab's `initState` runs once per session and never again. Anything that needs to re-fetch must listen to `RefreshSignal` (`lib/data/refresh_signal.dart`); it is fired on tab change, on app resume, and after a call is submitted.
- `ApiService` getters return `null` when a request fails (vs an empty list when the server genuinely has nothing). Screens must keep their existing data on `null` rather than blanking the list.
- Nothing derived from `CallVerification` / `CallRecord.verdictKind` / `finalResult` may be rendered in agent-facing UI (`call_view`, `call_summary_view`, `history_view`) — not the verdict, not the note, not "we checked your call log". It is computed and sent to the backend, and the agent is never shown that the check happened. There is no exception any more: the Dashboard's test-mode monitor has been removed, so no screen in the app renders a verdict.
- The History tab reads `CallHistoryStore` (on-device, `shared_preferences`) — the backend has no call-history endpoint. It is scoped to the logged-in agent, and shows only what the agent themselves reported (student, reason, outcome, duration, notes).
- Login is `POST /Auth/login` (unified, every role). The token it returns is accepted on **both** the `/call-tracker/*` routes and the root routes (`/ManagementStudent/*`, `/groups/:id/students`, `/reports`, `/rooms`, `/report-categories`, `/devices`). The old 403 on root routes came from the retired `/call-tracker/auth/login` token and is gone. What still differs is the **envelope**: call-tracker routes return bare JSON, root routes wrap in `{success, message, data}` — and `/reports` nests one level further (`data.data`) with flat `total`/`page`/`limit` instead of a `pagination` object, which is why `Paged` has both `fromJson` and `fromFlat`.
- Roles arrive spelled two ways: `/Auth/login` returns `team onsite` (space), `report_categories.role` returns `team_onsite` (underscore). `StaffRole.parse` in `models.dart` is the single normaliser — never compare a role to a raw string anywhere else.
- Teachers are refused at login and on restore (they have their own app), so `AuthGate` may assume the signed-in user is not a teacher. An unrecognised role is refused too, rather than dropped into an empty shell.
- `AuthService.restore()` paints from the cached session and re-checks the token with `POST /Token/verifyToken` **without blocking** — the API host cold-starts, so awaiting it would add seconds to launch. A session stored before roles existed (`v != 2`) is the one case that awaits, because it has no role to route on.
- `currentAgent()` / `restore()` must never throw: `main()` awaits `restore()` before `runApp`, so a throw there leaves the app with no first frame and no login screen — unrecoverable without clearing app data.
- Reports visibility is the backend's job (own-role categories plus your own submissions; everything for an admin). The app must never filter the reports list client-side — only the per-report action buttons are gated on the device, and that gate is cosmetic. A 403 from `PATCH /reports/:id/state` means "not your category" and must be shown, not treated as a dead session: `_isUnauthorized` deliberately fires on 401 only.
- Report photos are **camera-only** (`PhotoCapture.takePhoto`) — deliberately, so a problem is photographed where it is rather than attached from an old screenshot days later. Do not re-add a gallery source; the mobile app diverges from the dashboard's report modal on this one point. Captured at quality 70 / max width 1920, which is what keeps them under the backend's 10MB limit. The rest of the compose screen mirrors that modal (flag header, dashed photo card, all 23 categories as chips, required category); keep the two in step when either changes.
- `ReportApi.createReport` is the one call that returns *why* it failed (`({report, error})`) instead of a bare null, and the compose screen shows the server's own message. A report that will not send is the place where "check your connection" is actively misleading — the cause is usually a rejection the server already explained. A 2xx whose body cannot be parsed counts as sent, not failed, or the user files it twice.
- `/reports` pagination is flat (`total`/`page`/`limit`, no `totalPages`), so it needs `Paged.fromFlat`/`fromFlatItems`. `Paged.fromJson` is for the `pagination`-object endpoints (students, groups) — mixing them up silently yields a single page.
